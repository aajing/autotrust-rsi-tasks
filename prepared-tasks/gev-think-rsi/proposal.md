| Research Question | Scientific question | Can an autonomous research agent learn an external compute-allocation router that improves a frozen GEV model's free-response accuracy under fixed inference budgets, compared with fixed confidence-threshold escalation? The main language model, S1 head and solver prompts stay frozen; the small external router is trainable. Its only output is a permitted compute action, not an answer, tool argument or task-solving program. This tests allocation of additional reasoning and verification, not GEV weight self-evolution. |
| Research Question | Why this is scientific research rather than pure engineering optimization | The testable variables are routing features, allocation objectives, calibration, early stopping and whether to retain or replace a first answer. A useful router must detect confidently wrong answers and avoid spending tokens where extra reasoning hurts. AutoTrust's adaptive-thinking reports motivate this hypothesis: fixed-threshold escalation helped some reasoning datasets but harmed BANKING77 and barely changed ToolRet. Those findings are task-dependent, author-reported evidence, not this proposal's baseline. Matched cost ceilings and identical solver/tool implementations make algorithmic allocation the experimental variable. |

| Evaluation | Fixed evaluation protocol | Five equal free-response families each contain 100/20/40 train/dev/evaluation records, totaling 500/100/200. Every scenario group contains direct and compositional variants and remains in one split; 400 semantic fingerprints are distinct. Python varies arithmetic recurrences, comparisons and nested loops. SQL uses two tables with eight products and 12–24 orders, variable grouping/aggregates, compound filters and HAVING. Invoices use four/eight lines and invoice-level or per-line discount rounding before tax. Schedules use six/ten jobs, two resources and up to two predecessors. Workflows use four/eight transitions with optional cross-item precedence. Ordering is fixed and shuffled. All cases, gold and seeds are public; difficulty and adaptive-compute benefit are unmeasured. |
| Evaluation | Evaluation mode and input | Inputs are ordinary task requests and state, with a planned maximum 1,500 model tokens and free JSON/SQL/action outputs. The uniform trusted tools are bounded Python, read-only SQLite and the workflow simulator: two calls per item, five CPU seconds per call and 32 KiB output. Tools use staged task input and solver-generated content, not answer files. SQL denotations are checked on three publicly supplied databases; traces use bounded AST interpretation, schedules and workflows use exact constraints/state transitions. Gold remains excluded from the normal model interface by protocol. Actual tokenizer limits, process sandboxing and model/tool integration are pending; CPU oracles are implemented. |
| Evaluation | Reward or score definition | Let C be the number of fully correct instances among all 200. Score = 100 × C / 200, equivalent to the mean accuracy of the five equal families. A correct result must parse and satisfy the fixed family verifier; schedules and workflows must satisfy every requirement. Full marks are exactly 100 only if all 200 are correct, the evaluation completes and all scope/accounting limits pass. Ordinary incorrect, malformed or semantically incomplete answers receive zero for that item; there is no partial credit. At a per-item reasoning/tool cap, the controller returns the latest completed answer, which is scored normally. Invalid artifacts, process crashes, attribution failures, global timeouts or incomplete dataset evaluation are unscored rather than converted to accuracy zero. |
