| Research Question | Scientific question | On a fully disclosed fixed workload, can an autonomous research agent learn a compact external compute-allocation router that improves the frozen GEV model's free-response accuracy under fixed inference budgets over B0 confidence-threshold escalation? This is deliberately **benchmark-conditioned optimization**: all published inputs, answers and evaluation traces may inform fitting and selection. Frozen model weights, S1 head, prompts and tools generate every answer; the router outputs only a compute action. The endpoint measures achievable allocation improvement on this workload, not held-out generalization or GEV weight self-evolution. |
| Research Question | Why this is scientific research rather than pure engineering optimization | Test whether confidence-only escalation, learned feature-conditioned action values and budget-aware stopping allocate scarce inference differently when extra reasoning may help or harm. Public gold supports counterfactual action-value targets from charged model traces; successive candidate runs test those hypotheses against matched B0 and fixed-reconsideration controls. The permitted intervention is allocation, with solver, prompts, tool behavior and ceilings identical. Evaluation-specific compute choices encoded in the admitted router are allowed and must be reported; their success is evidence about this fixed workload only. Upstream adaptive-thinking results motivate the mechanism but are not this task's measured baseline. |
| Research Question | Starting environment and artifacts | The supplied stdlib package contains 500 learning, 100 development and 200 scoring records, all answers/checking databases, 400 distinct scenario groups, public seeds, exact verifiers, baseline JSON policies and SHA256 manifests. The traditional train/dev/evaluation names identify partitions, not fit exclusions: all are available for optimization. `scripts/export_work.py` includes every answer and seed without encryption. Original generators/data use Apache-2.0/CC0-1.0. Model orchestration, authentic accounting and official Harness integration are task-generation work; the present adapter fails closed rather than fabricating inference. |
| Research Question | Agent's final deliverable | A strict `router.json`, plus Work research code and a ledger of fitting data, hypotheses, charged model traces and selection decisions. Admitted artifacts are threshold policies or finite bounded JSON MLPs; no executable callbacks or output predictions. Judge reloads the complete materialized Work snapshot, admits only router data and generates fresh frozen-model answers. Each artifact is immutable within its Judge call; subsequent candidates may use all returned evaluation feedback. Solution copies the existing B0 without fitting, inference or evaluation. |
| Research Question | Files/components the agent may modify | Modify research/fitting programs, training sampling, routing objectives and the admitted external router. MLPs have exactly two ReLU hidden layers, widths at most 128 and at most 65,536 finite parameters, followed by five action logits. The fixed 72 features are a task-owned frozen 64-dimensional prompt-activation projection, S1 confidence/entropy, prompt/answer lengths, tool status and spent/remaining token/item counts. Projection extraction is pending runtime integration. Threshold schemas and deterministic tie-breaking are implemented in `policy.py`. Freeze solver prompts, model/adapter weights, features, tools, decoding, generators and score; do not expose task IDs as router features. |
| Research Question | Prohibited actions | No main-model/adapter fine-tuning, model replacement, solver-prompt optimization, extra models/APIs, handwritten task solvers, runtime answer tables, executable serialization, candidate inference callbacks or evaluator changes. | Reference Baseline | Baseline evaluation path | Judge loads all routers with the same trusted controller. Each instance starts with a greedy 128-token draft, thinking disabled, and an S1 correctness estimate using frozen `calibration_gold.json`. Actions are return-current, reconsider with a 256/512/1,024-token cap including thinking, or one tool-assisted checking pass capped at 512 generated tokens. At most two reconsiderations and one checking pass are allowed. Tool arguments and answers come only from the frozen solver. S1 refreshes, optional generation and mandatory calls all count. Answers follow the family-specific free-response schema. |
| Reference Baseline | Baseline metric reported by the repository | No score exists for this proposed free-response benchmark. The source reports 73.3% S1, 83.4% adaptive and 83.8% always-think accuracy over 1,754 calibration questions, with escalation on 47.8%; these were option-based questions and do not establish a new baseline. GEV's reported B200 timings and estimated adaptive latencies are not H100 measurements. | Evaluation | Fixed evaluation protocol | Five equal free-response families each contain 100/20/40 train/dev/evaluation records, totaling 500/100/200. Every scenario group contains direct and compositional variants and remains in one split; 400 semantic fingerprints are distinct. Python varies arithmetic recurrences, comparisons and nested loops. SQL uses two tables with eight products and 12–24 orders, variable grouping/aggregates, compound filters and HAVING. Invoices use four/eight lines and invoice-level or per-line discount rounding before tax. Schedules use six/ten jobs, two resources and up to two predecessors. Workflows use four/eight transitions with optional cross-item precedence. Ordering is fixed and shuffled. All cases, gold and seeds are public; difficulty and adaptive-compute benefit are unmeasured. |
| Evaluation | Evaluation mode and input | Inputs are ordinary task requests and state, with a planned maximum 1,500 model tokens and free JSON/SQL/action outputs. The uniform trusted tools are bounded Python, read-only SQLite and the workflow simulator: two calls per item, five CPU seconds per call and 32 KiB output. Tools use staged task input and solver-generated content, not answer files. SQL denotations are checked on three publicly supplied databases; traces use bounded AST interpretation, schedules and workflows use exact constraints/state transitions. Gold remains excluded from the normal model interface by protocol. Actual tokenizer limits, process sandboxing and model/tool integration are pending; CPU oracles are implemented. |
| Evaluation | Reward or score definition | Let C be the number of fully correct instances among all 200. Score = 100 × C / 200, equivalent to the mean accuracy of the five equal families. A correct result must parse and satisfy the fixed family verifier; schedules and workflows must satisfy every requirement. Full marks are exactly 100 only if all 200 are correct, the evaluation completes and all scope/accounting limits pass. Ordinary incorrect, malformed or semantically incomplete answers receive zero for that item; there is no partial credit. At a per-item reasoning/tool cap, the controller returns the latest completed answer, which is scored normally. Invalid artifacts, process crashes, attribution failures, global timeouts or incomplete dataset evaluation are unscored rather than converted to accuracy zero. |

Example: on an invoice request, the frozen solver writes the answer. The router may request a bounded reconsideration or checking pass, and may be trained using this public case's known outcome. It cannot return the known total itself. The measured result is improved computation allocation on this disclosed workload.
